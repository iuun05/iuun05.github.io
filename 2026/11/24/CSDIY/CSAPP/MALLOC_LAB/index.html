CS:APP malloc lab 笔记

malloc lab 可以说是 CS:APP 最复杂的一个实验了，里面涉及大量的指针操作和应用。在这个实验中，我们需要手动的去实现一个动态内存分配器，总共需要实现四个函数 init/malloc/free/realloc。我们需要在保证内存利用率前提下，提高性能。通过被这个 lab 拷打之后，会对指针和内存管理有更深的理解。

辅助函数

memlib.c 模块为你的动态内存分配器模拟底层内存系统。你可以在代码中调用 memlib.c 提供的以下接口函数：

  • void *mem_sbrk(int incr)：将堆向高地址扩展 incr 个字节（其中 incr 必须是非零正整数），并返回指向新分配堆区域第一个字节的通用指针（void *）。其语义与 Unix 的 sbrk 函数相同，唯一区别在于 mem_sbrk 仅接受非零正整数参数（不支持传 0 或负数来查询或收缩堆）。
  • void *mem_heap_lo(void)：返回指向当前堆区第一个字节的通用指针（堆底地址）。
  • void *mem_heap_hi(void)：返回指向当前堆区最后一个字节的通用指针（堆顶最高有效字节地址）。
  • size_t mem_heapsize(void)：返回当前堆的总大小（以字节为单位）。
  • size_t mem_pagesize(void)：返回系统的内存页大小（以字节为单位，在 Linux 系统上通常为 4K，即 4096 字节）。

评估

Malloc Lab 的性能指标（Performance Index）综合评估空间利用率与吞吐量，计算公式如下：

P=wU+(1−w)min⁡(1,TTlibc)P = wU + (1 - w)\min\left(1, \frac{T}{T_{\text{libc}}}\right) P=wU+(1−w)min(1,Tlibc​T​)

  • UUU（空间利用率）：有效载荷峰值与堆总大小的比值，权重 w=0.6w = 0.6w=0.6（满分占 606060 分）。
  • TTT（吞吐量）：每秒完成的内存操作数（Kops），与系统标准库 libc 吞吐量 TlibcT_{\text{libc}}Tlibc​ 对比，权重 1−w=0.41 - w = 0.41−w=0.4（满分占 404040 分，达到 TlibcT_{\text{libc}}Tlibc​ 即拿满）。

核心原则：由于两项指标各自存在得分上限（60%60\%60% 与 40%40\%40%），单方面追求极致吞吐量或极致空间利用率都无法获得高分，必须在两者之间取得均衡优化。

知识回顾

堆

动态分配器维护者一个进程的虚拟内存区域叫做堆，堆的生长方向和栈相反，堆是向上生长的，也就是说地址是逐渐增大的。然后堆顶存在一个指针，叫做 brk 指针。

写代码时堆的完整布局是：对齐填充块（4B） + 序言块（Prologue，8B，由紧挨着的已分配 Header 和 Footer 组成，永远不释放） + 普通数据块区 + 结尾块（Epilogue，4B，大小为 0、状态为已分配的 Header）

块

分配器是将堆按照块进行维护的，每一个块是一个连续的虚拟内存片，要么是已分配的，要么是空闲的。

已分配的块是不能被任何的操作修改，直到他被释放，释放方式可以分为显示进行分配或者被隐式分配（GC）。

然后每一个块为了操作系统方便处理，会进行一些对齐操作，具体来说，在 32 机器上快的倍数位 8 的倍倍速，64位机上为 16 的倍数。

一个块包含的部分有：

  • 头部：头部包含两部分，由于块大小总是 8 的倍数，那么最低的三位就总是 0，那么我们就可以借助这三位来储存额外的信息（0 位为块是否被分配，1 可以表示前一块是否被分配）
  • 有效载荷：这一部分不允许为空，是数据存储的部分。
  • 填充：是为了对齐额外添加的部分

虽然我们不能修改已分配的块，但是我们可以堆空闲块进行一系列的操作，把他们组成易于管理的数据结构。

隐式空闲链表

我们根据块头部的大小隐含的将每一块串联成链表的格式，如下图：

这种结构称为隐式链表，我们借助头部就可以直接的访问每一个块，我们设置了一个已分配，并且块大小为 0 的块作为结尾

隐式空闲链表优点是简单，缺点就是任何的操作都是线性的。

显示空闲链表

由于隐式链表结构简单，操作和块数量呈线性关系，因此不适用于通用分配器，我们可以在有效负载中存入对应的指针，将块以链表的方式组织起来（也可以把他们组织为二叉树等其他数据结构）

显式链表通常用 pred/succ 指针实现双向移动，脚部（Footer）的核心作用是支持 O(1)O(1)O(1) 时间的物理前一块边界标记合并（Boundary Tag Coalescing）——释放当前块时，通过读取 前一块的脚部 才能立刻知道物理上紧挨着的前一块是否空闲以及它的大小，而不用从堆头遍历。

去脚部优化：既然在头部第 1 位存了 prev_alloc（前一块是否分配），那么已分配块不需要脚部（省下 4 字节开销给有效载荷），只有空闲块才需要保留脚部供合并使用。

分离的空闲链表

单向链表和块的数量是呈现线性关系的，因此我们可以维护多个空闲链表，我们将块的大小按照一定的方式进行分类，比如按照 2 的幂进行划分。

其中有两种的基本方法：

  • 简单储存：每个大小类的空闲链表只包含固定大小的块（例如 16B、32B、64B 等）。当某个链表为空时，分配器向系统申请一整页（如 4KB），并将其切分成若干个该固定大小的块串入链表。
    • 分配和释放：分配时直接从对应大小的链表头部取出一块（O(1) 时间），如果块比请求略大也绝不分割；释放时直接把块插回原链表头部，也绝不与相邻块合并。
  • 分离适配: 维护一个空闲链表数组，每个链表对应一个大小区间（如 {16}、{17~32}、{33~64}、{65~128}…）。根据请求大小定位到对应的大小类链表，在链表中搜索合适的块（首次适配或最佳适配）。如果当前链表找不到，就向更大的大小类链表继续查找；找到后，如果剩余空间足够大，则将块分割，把余下的部分插入对应的新大小类链表中。
    • 分配：分离适配的分配是在对应大小类链表中搜索合适块（找不到则去更大的桶找），找到后若剩余空间达到最小块阈值，则分割并将剩余部分插入对应桶中。
    • 释放：释放块时，会立即与物理上相邻的空闲块进行边界标记合并，并将合并后的新块插入到对应大小类的空闲链表中。

分离存储是“固定切分、只进不出、不合不拆”，追求极致速度但碎片严重；分离适配是“按区间分桶、可拆可合”，在速度与空间利用率之间取得了最佳平衡。

最小块大小（Minimum Block Size）：在显式/分离空闲链表中，一个空闲块至少要容纳 Header(4B) + pred(4B) + succ(4B) + Footer(4B) = 16B（如果是 64 位指针则是 24B 或 32B）。

块的合并

主要有四种情况：

  • 前已分配后已分配（不合并）
  • 前已分配后空闲（向后合并）
  • 前空闲后已分配（向前合并）
  • 前后都空闲（三块合一）

合并时机

  • 立即合并（Immediate Coalescing）
  • 推迟合并（Deferred - Coalescing）

Malloc Lab 推荐立即合并，防止碎片累积

放置策略与链表插入顺序

  • 搜索策略
    • 首次适配（First Fit）
    • 下一次适配（Next Fit）
    • 最佳适配（Best Fit）
  • 插入顺序
    • LIFO（后进先出，插在链表头，O(1) 但碎片略多）
    • 地址顺序（按内存地址排序插入，释放稍慢但利用率更高）

内存碎片

碎片主要是存在两种形式：

  • 内部碎片：为了对齐，或者冗余导致单个块中除了有效数据，还有其他未使用的部分
  • 外部碎片：现有块总体足够分配，但是分布过于分散导致无法被使用，只能向操作系统再次申请

显示空闲链表

我们在隐式空闲链表的基础进行进一步优化，我们将前驱指针和后序指针存放到有效负载中。因此最小块大小通常要从隐式链表的 8B 扩大到 16B

Header4B+pred4B+succ4B+Footer4B=16BHeader 4B + pred 4B + succ 4B + Footer 4B = 16B Header4B+pred4B+succ4B+Footer4B=16B

我们维护一个 free_listp 节点，用来串起所有的空闲块。然后实现 insert_node 和 delete_node 函数。进行插入和删除的时机主要是：产生和消耗空闲块的时候。

具体来说，我们进行操作的时机主要有：

  • 申请新的内存块的时候:向系统 mem_sbrk 扩展出新的空闲区域并初始化为空闲块后，立即调用 coalesce（内部会先 delete_node 掉可能存在的原堆尾空闲块，再 insert_node 合并后的整块）。
  • 分割内存的时候:
    • 先调用 delete_node(bp) 将当前选中的空闲块从空闲链表中摘除；
    • 如果剩余空间达到最小块要求，切分出剩余块并调用 insert_node 插回空闲链表。
  • 释放内存块的时候: 修改块头部/脚部状态为空闲后，进入 coalesce 处理链表更新。
  • 合并空闲块的时候:
    • 前后都已分配：直接 insert_node(bp)；
    • 前已分配、后空闲：delete_node(NEXT_BLKP(bp)) →\rightarrow→ 合并 →\rightarrow→ insert_node(bp)；
    • 前空闲、后已分配：delete_node(PREV_BLKP(bp)) →\rightarrow→ 合并 →\rightarrow→ insert_node(PREV_BLKP(bp))；
    • 前后均空闲：同时 delete_node 前后两个旧空闲块 →\rightarrow→ 三块合一 →\rightarrow→ insert_node(PREV_BLKP(bp))。

特别注意的是，在 mm_init 开始的时候一定要 free_listp = NULL; 不要再全局变量中设置为 NULL。因此测试的时候是直接调用 mm_init，如果在全局变量开始初始化会导致下一轮评测中出现脏数据。

分离空闲链表

在显式空闲链表的基础上，我们将单一的全局空闲链表扩展为空闲链表数组（大小类桶数组 free_list_bucket[]），将不同大小区间的空闲块隔离到对应的桶（Bucket）中管理：

根据块大小 size（通常按 2 的幂次或细分阶梯划分，如 {16},{17∼32},{33∼64},…,{1<<BUCKETSIZE∼∞}\{16\}, \{17\sim 32\}, \{33\sim 64\}, \dots, \{1 << BUCKETSIZE\sim \infty\}{16},{17∼32},{33∼64},…,{1<<BUCKETSIZE∼∞}），通过位运算或循环移位快速计算出对应的桶下标 index。

更新后的插入与删除逻辑：

  • 插入（insert_node(bp)）：先根据当前块的大小计算 index，再采用 LIFO（头插法） 将节点插入到 free_list_bucket[index] 的链表头部（或按地址有序插入以提高空间利用率）。

  • 删除（delete_node(bp)）：同样先根据块大小计算它所属的桶下标 index，然后在 free_list_bucket[index] 中修改其前驱 pred 和后继 succ 指针将其摘除（若删除的是桶的头节点，需同步更新 free_list_bucket[index] 指向后继节点）。

已分配块的 foot 优化

在测试的时候没有发现有什么明显的长进，不知道是不是我实现有问题，因此这部分优化存疑

脚部（Footer）的唯一作用是在释放（free）当前块时，让物理后一块能够通过读取前一块的脚部来合并。如果前一块本身处于“已分配”状态，它根本不会被合并，因此它的脚部完全是冗余开销。

由于块大小始终按 8 字节对齐，头部（Header）的最低 3 位恒为 0：

  • 第 0 位（0x1）：标记当前块是否已分配（ALLOC）。
  • 第 1 位（0x2）：借用这一位来标记物理前一块是否已分配（PREV_ALLOC）。

这样，当释放当前块并需要向前合并时，只需检查当前块 Header 的第 1 位：

  • 若 PREV_ALLOC == 1：前一块已分配，无需访问其脚部，直接跳过向前合并；
  • 若 PREV_ALLOC == 0：前一块为空闲块（保留着完整的 Header 和 Footer），正常通过 PREV_BLKP(bp) 读取其脚部完成合并。

影响部分：

  • 初始化序言块与结尾块（mm_init）：

    • 序言块（Prologue）始终视为已分配；
    • 紧跟在序言块后的结尾块（Epilogue）在初始化时，必须将 Header 设为 PACK(0, 1) | 0x2（标记前一块即序言块已分配）。

  • 分配与分割块（place）：

    • 分配块时不再写入当前块的 Footer，写入 Header 时注意保留原本的 PREV_ALLOC 位；
    • 若未发生分割：必须更新物理下一块的头部状态；
    • 若发生分割：前半部分（已分配）设好状态，后半部分的 Header 需让 PREV_ALLOC = 1，而新空闲块之后的物理下一块本身的前一块就是这个新空闲块，保持 PREV_ALLOC = 0。

  • 释放与扩展堆（mm_free / extend_heap / coalesce）：

    • mm_free(bp) 释放当前块时，除了把当前块设为未分配并写入自己的 Footer 外，必须清除物理下一块 Header 中的 PREV_ALLOC 位；

    • extend_heap 新申请出空闲块后，需从旧结尾块（Epilogue）的 Header 中继承 PREV_ALLOC 位，写入新空闲块的 Header，并将新结尾块设为（此时前一块是新空闲块，故 PREV_ALLOC 为 0）

分情况优化 realloc

主要思路和合并空闲块的思路一致：

  • 如果当前的块大小足够新的 adj_size（对齐之后的字节大小），那么我们就直接返回原指针即可。
  • 查看加上 右/左 边的内存是否可以补充到 adj_size（对齐之后的字节大小），如果可以，那么我们就选择吞并 右/左 边的空闲块
  • 如果靠近结尾，或者隔着空闲块靠近结尾，那么直接进行准确分配
  • 如果走投无路，只能新开一块内存，然后将数据复制过去。
  1. 在立即合并（Immediate Coalescing）策略下，堆中不会存在两个物理相邻的空闲块，因此右侧最多只需检查紧邻的那一块空闲块以及它是否直通堆尾即可。
  2. 由于后续可能继续扩容，保留适度余量反而能避免频繁切割与重新分配，因此我们需要留有一定的冗余

移除向左吞并逻辑

向右吞并是纯原地扩容（ptr 地址不变），不需要调用 memcpy，零数据搬移开销；

向左吞并（当前块左侧是空闲块）虽然不需要重新 malloc 新块，但因为有效载荷的起始地址向前移动了，必须使用 memmove（注意不能用 memcpy，因为新旧内存区域存在重叠！） 将原数据搬移到新载荷开头。

由于需要复制数据到新的地址上，十分的耗费时间，由于没有配置冗余，我们直接去除向左吞并逻辑，可以使 realloc 性能进一步提升

向右吞并的分割大块

当向右吞并相邻空闲块后，若剩余空间大于分割阈值(THRESHOLD)，则切分出新空闲块归还链表，避免内部碎片：

  1. 摘除旧块：先调用 bucket_delete_node(next_bp) 移除原右侧空闲块。
  2. 切分判断：
    • 够切分：更新当前块 Header 为 adj_size（保留原 PREV_ALLOC，不写 Footer）；初始化剩余块的 Header（置 PREV_ALLOC = 1）与 Footer，最后 bucket_insert_node(rem_bp)。
    • 不够切分**：全盘吞并 total_size，更新当前块 Header，并调用 SET_PREV_ALLOC 标记物理下一块。

调优技巧：适当提高分割阈值，可在当前块尾部保留缓冲余量，使后续小步长 realloc 直接命中原地扩容，减少链表操作开销。 其实，这里照单全收是最优解…

后续优化

前方还有很多优化方向，以后再来探索吧：

  • 数据结构升级（从链表到红黑树）：当某个大块大小类桶中的空闲块数量较少时，继续沿用双向链表保持低常数开销；一旦节点数量增多，可将大块桶切换为红黑树（类似 dlmalloc 的 BinTree 设计，八股文照进现实），将最坏搜索时间从 O(N)O(N)O(N) 降到 O(log⁡N)O(\log N)O(logN)。
  • 精细化适配策略（近似最佳适配）：在分离链表中采用 “有限步数的最佳适配（Best-Fit with Limited Search）”——命中首个满足条件的块后，继续向后探查固定步数（如 5∼105\sim 105∼10 个节点）挑选体积最贴合的块，在几乎不损失吞吐量的前提下进一步榨干空间利用率。
  • 细粒度大小类分桶（Fine-grained Size Classes）：针对高频小块（如 16B∼128B16\text{B}\sim 128\text{B}16B∼128B）按 8B8\text{B}8B 或 16B16\text{B}16B 等差密分桶，大块再按 222 的幂次分桶，使小块桶直接退化为“精确命中、零内部碎片、无需分割”的快速通道。
  • 地址有序插入（Address-Ordered Policy）：将链表插入策略从 LIFO 改为按内存地址升序插入，优先复用低地址区域的空闲块，从根源上抑制堆顶无意义抬升（降低外部碎片）。
